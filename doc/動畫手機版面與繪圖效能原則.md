# 動畫手機版面與繪圖效能原則

適用於 JHphysics 往後新增或修改的互動動畫，尤其是手機橫向、內建瀏覽器或 App 內瀏覽器。這些瀏覽器可能有較高的上下工具列，網頁可用高度會小於手機螢幕高度。設計與測試都應以網頁**實際取得的容器尺寸**為準。

## 一、畫面與形狀：先保住比例

1. 每個動畫先定義固定的「邏輯場景」寬高，例如 `800 × 400`。物體位置、半徑與碰撞計算均使用此座標系。
2. 控制區、標題與導覽先分配空間，再量測場景容器的可用寬 `W`、高 `H`。不要假設手機螢幕尺寸就是網頁可用尺寸。
3. 用**同一個**縮放比例 `s = min(W / 場景寬, H / 場景高)`。顯示寬、高分別為 `場景寬 × s`、`場景高 × s`，並在容器中置中。剩餘空間留白；不可讓 X、Y 軸各用不同的比例去填滿容器。
4. CSS 與 JavaScript 必須遵守同一組尺寸。避免同時設定 `canvas { width: 100%; height: 100%; }`，卻仍用固定邏輯寬高繪圖。`object-fit: contain` 不能代替 Canvas 繪圖座標的等比例轉換。
5. 點擊、拖曳等互動須使用相同的縮放比例與置中偏移，把指標座標轉回邏輯場景座標。否則圖形看似正確，點擊位置仍會錯。
6. 容器尺寸、橫直向或瀏覽器工具列高度改變時，重新量測並重繪。可用 `ResizeObserver` 觀察場景容器，並以實機確認內建瀏覽器開合工具列時的行為。`100dvh` 可協助配置高度，但不能修正場景拉伸。
7. 畫面真的不足時，優先讓控制區換行、收合或在控制區內捲動；場景仍等比例縮小。須保留可辨識的字與可點擊的控制項，不要用極小字體勉強塞滿。

### 現有 Chapter3 範例

`book2/Chapter3` 四個動畫目前都會取得 Canvas 的實際矩形尺寸，再以 `canvas.width / 場景寬` 與 `canvas.height / 場景高` 分別縮放 X、Y。當手機內建瀏覽器的工具列壓縮可用高度時，兩者不同，圓球可能變橢圓。部分頁面又以 `width: 100% !important; height: 100% !important` 強制 Canvas 填滿剩餘空間。修改時應先統一這兩處的尺寸規則，再調整控制區。

## 二、Canvas 清晰度：顯示尺寸與像素尺寸分開

Canvas 是點陣繪圖表面，但線條、圓形與文字可在每次重繪時依目前解析度重新光柵化，**不必因為它是 Canvas 就接受模糊畫面**。

- CSS 寬、高決定畫面佔用多少空間，且須符合上一節的場景比例。
- Canvas 的 `width`、`height` 屬性決定背後的像素數。可依顯示尺寸乘上有效 DPR（`devicePixelRatio`）設定，然後以相同的比例轉換繪圖座標。
- 每次改變 Canvas 的像素尺寸會清空內容並重設繪圖狀態；應只在尺寸確實變化時設定，隨後重設 transform 並重繪。
- 解析度不應無條件拉到手機的最高 DPR。以有效 DPR 上限 **2 作為起點**，再依實機的清晰度和效能調整。這是專案的初始策略，不是所有手機都適用的固定規範。

像素成本與 DPR 的**平方**成長。若顯示尺寸是 `800 × 400` CSS 像素，DPR 1、2、3 分別約需 32 萬、128 萬、288 萬像素；還沒算每幀繪圖與其他緩衝成本。因此「提高解析度」須有清晰度收益及手機量測結果支持。

## 三、手機效能：以實測決定優化

1. 動畫用 `requestAnimationFrame` 驅動；暫停、頁面隱藏或動畫結束時停止不必要的更新與重繪。靜態畫面只在狀態或尺寸變動時重繪。
2. 物理模擬的時間步進與繪圖幀率分開處理，避免較慢手機上的運動速度隨幀率改變。
3. 避免每幀讀取版面尺寸、重設 Canvas 像素尺寸或重畫完全不變的複雜背景。先找出真正耗時的部分，再考慮快取背景、簡化陰影與漸層、減少繪圖呼叫。
4. 在實際手機的內建瀏覽器及 Chrome 等主要瀏覽器測試：觀察連續播放時是否掉幀、觸控回應、裝置發熱與耗電。若畫質與流暢度衝突，可比較有效 DPR 2、1.5、1 的實測結果；不要只憑桌機模擬器決定。
5. 以畫面穩定與操作順暢為驗收目標。60 fps 約有每幀 16.7 ms 的時間預算；若場景不需要 60 fps，穩定的較低更新率也可接受，但速度與互動仍須正確。

## 四、何時使用 SVG

SVG 適合**少量、幾何形狀明確**的圖：球、方塊、軌道、箭頭、標籤，以及需要個別點擊的物體。以 `viewBox` 定義邏輯場景並等比例顯示，線條和文字在不同尺寸通常較銳利，也容易對單個圖形綁事件。往後新增這類簡單教學圖，可以優先評估 SVG。

Canvas 適合物件較多、畫面頻繁整體重繪或需要逐像素效果的動畫。現有 Chapter3 場景物件少，SVG 在技術上可行；但**不建議只為了解決拉伸而全面改寫**。先修正等比例配置及 DPR，檢查實機清晰度與效能，再決定是否有轉換收益。SVG 也有 DOM、樣式計算與重繪成本，不能假設它一定比 Canvas 快。

可混用：靜態說明、標籤或控制項用 HTML/SVG，頻繁變化的場景用 Canvas。但只在實測或維護需求支持時採用，避免為簡單動畫增加座標同步負擔。

## 新動畫交付檢查

- [ ] 手機橫向、內建瀏覽器工具列較大時，場景完整可見，圓仍為圓，方塊比例不變。
- [ ] 工具列開合、旋轉與視窗尺寸變動後，圖形、標籤及點擊位置仍正確。
- [ ] 控制項可閱讀、可觸控；空間不足時不壓扁場景。
- [ ] Canvas 的 CSS 尺寸、像素尺寸、邏輯座標與 DPR 各有明確用途；僅在必要時調整解析度。
- [ ] 用實際手機檢查連續播放的流暢度與清晰度，記錄測試瀏覽器及有效 DPR。
